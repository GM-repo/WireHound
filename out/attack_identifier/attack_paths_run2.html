Benign twin
A monitoring agent polling a SaaS endpoint, plus an administrator using WinRM and then browsing a share. This is the explanation to disprove.
What confirms it
Registration age and hosting of the C2 domain; process ancestry on 10.90.7.30 at 00:03 and 09:14; whether the NTLM identity on hop two has ever authenticated from 10.90.7.61 before; what was read on 10.90.7.80.
Note on C-2
The movement-chain characteristic was judged No this run on the reasoning that the two hops use different protocols and are 27 minutes apart, so they do not match the tight same-protocol chain the characteristic describes. C-1 and F-23 carry the same finding and both say Yes.

The pacing is the tell. A script chains hops in seconds. Twenty-seven minutes between WinRM and the onward SMB connection, then another twenty-two before the check-in, is the cadence of a human working interactively. Set against a beacon that never pauses for 24 hours, this reads as hands-on-keyboard activity riding an automated implant.

T1571 Non-Standard Port · T1001.003 Protocol or Service Impersonation · T1095 Non-Application Layer Protocol · T1572 Protocol Tunneling
Why this deserves attention
"Wrong protocol on the right port" is the strongest of the three port tests in the hunt catalogue, precisely because it is how tunnels and custom C2 hide behind an allowed egress rule. Here it fires across the entire estate and the analyzer failure is unambiguous.
Benign twin
Real and plausible. A proprietary mail client or a vendor sync protocol sharing the IMAP port would look identical, and the topology does show genuine parsed imap and imap/imf traffic to the same server. Zeek Binpac exceptions on IMAP are also common with unusual literals and IDLE handling.
The test that settles it
Carve one of these sessions from the PCAP and identify the first bytes. If it is a documented mail-client dialect, close it and tune the analyzer. If the payload is opaque or high-entropy, this is a fleet-wide covert channel and outranks Path B.

Do these form one operation?

There is a coherent story joining four of the seven, and it should be held as a hypothesis rather than a conclusion.

The composite reading. An administrative credential is broadcast in cleartext across the estate all day (C). An implant on the management workstation has been beaconing since before the capture opened (A), and mid-morning an operator uses that channel to execute on ws-fin07 and reach the file server (A). Three hours earlier a service account pulls a database dump with its data channel aimed at an address that does not exist in this network (D). Late in the day a host that has never spoken HTTP emits a single request whose only payload is an instruction to a language model to disregard its instructions (G).

Each is individually explainable. The combination — a persistent channel, a credential exposure that would supply it, a rare off-network transfer, and an anti-analysis payload — is the shape of an intrusion in its collection phase.

What argues against a single operation: the segments are genuinely isolated in the topology. There is no observed edge between 10.30.0/9 and 10.90.7, so Path A's actor and Path C's exposed credential live on networks that never touch in this capture. Paths B, E and F are each better explained by ordinary operations than by an adversary. Treating all seven as one campaign would over-fit the evidence.

The defensible position: Path A is a live intrusion. Path D is an unexplained data movement that must be resolved today. Path C is a standing exposure that would explain a great deal if the intrusion spreads. Paths B, E, F and G are open questions with specific, cheap tests attached.

What this capture cannot tell you

  • No external visibility. All 61 nodes are internal. Every internet destination is inferred from TLS SNI at a proxy hop, so C2 attribution, domain age and hosting reputation are unavailable from this data.
  • The beacon predates the capture — it is already running three minutes in. Initial access happened before this window.
  • No packet payloads. Verdicts rest on Zeek metadata. What the WinRM session executed, what the SMB session read, what db_dump contained, and what the port-143 sessions carry are all outside this evidence.
  • Aggregate queries lose time. O-4 reports a 250 s maximum gap without saying when — precisely what Path F needs.
  • One capture, no baseline. "First-seen" and "rare" mean within 24 hours. A longer history would sharpen every rarity-based finding and dissolve some of them.
  • Verdicts are not stable across adjudication runs on identical evidence — see the section above.
